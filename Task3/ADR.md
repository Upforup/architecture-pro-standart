### Логика принятия решений и выбора технологий

1. Было принято решение перевести интернет банк на микросервисную архитектуру для обеспечения требования +R4, +R5, +R10: текущая версия платформы не совместима с Kafka. Для обхода этого ограничения предлагается реализовать сервис депозитов. Запросы на оформление заявок будут маршрутизироваться на новый сервис через API Gateway 
   1. Реализация сервисов на java/Spring (уже используется в других системах, есть экспертиза), совместимо с Kafka (+R3)
   2. Бд: PostgreSQL: уже иcпользуется, есть экспертиза, бесплатно (+R3)
2. Kafka в качестве брокера сообщение (+R4)
3. Для интеграции АБС с ИБ предлагается реализовать отдельный сервис - интеграционный адаптер (Java), таким образом исключаются прямые вызовы АБС для онлай подачи заявок. 
4. Обработку ставок необходимо реализовать в АБС (R2). Публикация ставок  в топик Kafka будет реализована интеграционным сервисом. Потребители: сайт и ИМ - читают и кэшируют (+R9).


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Отдельный кэш ставок** Можно развернуть отдельный инстанс специализированного кэша для хранения справочных данных. Но в рамках MVP достаточно будет кешировать только ставки, проще и дешевле это пока делать напрямую в сервисах, не ожидается большое количество данных. 
2. **Отложить внедрение брокера сообщений** На этапе MVP можно обойтись специальным процессом, который по расписанию бы выполнял требуемую работу асинхронно.

**Недостатки, ограничения, риски**

1. Клиентский путь для новых клиентов по прежнему подразумевает личное обращение в отделение (Идентификация).
2. Ставки и заявки по прежнему обрабатываются вручную сотрудниками бэк офиса.
3. Ограничение масштабирования АБС сохраняется.
4. Delphi в АБС (устаревшая технология)
5. Риск потери сообщений в Kafka (без подтверждения доставки)
