### <a name="_qmphm5d6rvi3"></a>**Решение**

[Диаграмма контекста](Standard%20context%20diagram.png)

[Диаграмма контейнеров](Standard%20container%20diagram.png)

**Архитектурное решение:**

1. **Собственный кол-центр банка** получает ставки через Kafka:
   - Менеджер бек-офиса обновляет ставки в АБС
   - АБС-адаптер публикует ставки в топик Kafka
   - Система кол-центра подписывается на топик и кэширует ставки в БД

2. **Партнёрский кол-центр** получает ставки через SFTP:
   - Перекладчик Kafka/SFTP подписывается на тот же топик Kafka
   - При изменении ставок формируется CSV-файл
   - Файл выгружается на SFTP-сервер банка
   - Партнёрский кол-центр забирает файл по расписанию

### Логика принятия решений и выбора технологий

1. **Использование Kafka** (+R1): ставка уже публикуется в Kafka для интернет-банка (Task3), кол-центр просто подписывается на этот же топик. Это соответствует требованию +R4 (Kafka как брокер сообщений) и +R3 (максимум использования существующих технологий).

2. **Перекладчик Kafka/SFTP на Java/Spring**: соответствует требованию +R2 — используем существующую экспертизу банка. Java-сервис легко интегрируется с Kafka.

3. **Формат файла CSV**: прост и универсален, партнёры могут обрабатывать его без сложного парсинга. UTF-8 обеспечивает поддержку кириллицы.

4. **Отсутствие прямого API для партнёра**: обусловлено ограничением партнёрского кол-центра — нет возможности делать API-вызовы.

5. **SFTP-сервер банка**: управляемый компонент, который обеспечивает безопасность передачи (шифрование) и доступность (R4).

6. **Накопление файлов при недоступности**: реализуется через очередь в перекладчике — файлы формируются и сохраняются локально до успешной выгрузки.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Прямая выгрузка из АБС на SFTP**
   - АБС формирует файл и выгружает на SFTP напрямую
   - *Недостаток*: дополнительная нагрузка на АБС, нарушение принципа минимальных прямых интеграций (+R3)

2. **Выгрузка через API кол-центра**
   - Партнёрский кол-центр вызывает API системы кол-центра для получения ставок
   - *Недостаток*: противоречит ограничению партнёра (нет возможности делать API-вызовы)

3. **Email-рассылка ставок**
   - Отправка файла по email при изменении ставок
   - *Недостаток*: ненадёжно, нет гарантии доставки, сложно автоматизировать обработку

4. **Облачный файловый storage**
   - Выгрузка файлов в облачное хранилище (S3, etc.)
   - *Недостаток*: дополнительные затраты, вопросы безопасности (вынос данных за периметр банка)

**Недостатки, ограничения, риски**

1. **Задержка актуальности ставок**: партнёрский кол-центр получает ставки с задержкой (зависит от расписания забора файлов с SFTP), в отличие от собственного кол-центра (почти реальное время через Kafka).

2. **Несинхронизация**: возможно рассинхронизация ставок между собственным и партнёрским кол-центрами в период между изменением ставок и забором файла.

3. **Зависимость от SFTP**: при недоступности SFTP-сервера партнёры не получат актуальные ставки.

4. **Отсутствие подтверждения прочтения**: банк не знает, получил ли партнёрский кол-центр файл.

5. **Ограниченный формат**: CSV не позволяет передавать сложные структуры данных (например, иерархию продуктов, персональные предложения).

6. **Риск потери файлов**: при ошибках SFTP-выгрузки файлы могут быть потеряны без уведомления.

7. **Масштабируемость**: при увеличении количества партнёров потребуется управлять правами доступа и мониторить активность на SFTP.
